# チェックリスト

Streamlit + Gemini API のこのアプリで、実際に問題になりやすい項目です。項目の説明は Streamlit 1.66 で確認した内容です。バージョンが変わったら、`.venv/Lib/site-packages/streamlit/config.py` で初期値を確かめてください。

## 1. APIキーと秘密の情報

このアプリで一番の財産は Gemini の APIキーです。流出すると、他人に使われて料金や利用枠の被害が出ます。

- コードや `.env.example`、`README.md` に本物のキーが書かれていないか。
- `.gitignore` に `.env` と `.streamlit/secrets.toml` が入っているか。
- **git を使っていないので `.gitignore` は何も守っていない。** フォルダごと ZIP で渡す、クラウド同期する、GitHub に手動でアップロードすると `.env` も一緒に出ていく。共有の予定があるときは必ず伝える。
- キーがログ、画面、エラー文、ダウンロードするファイルに出ないか。
- サイドバーで入力したキーが `st.session_state` 以外（ファイルなど）に保存されていないか。

## 2. ネットワークと接続

- `.streamlit/config.toml` に `server.address` があるか。**未設定だと全てのネットワークの入口で待ち受ける**ので、ファイアウォールの設定によっては同じ Wi-Fi の機器からアプリを開ける。起動時に表示される Network URL がそのサインです。
  - 自分だけで使うなら、次の設定で自分の PC からしか開けなくなる。

    ```toml
    [server]
    address = "localhost"
    ```

- `server.enableCORS` と `server.enableXsrfProtection` が `false` にされていないか。初期値はどちらも `true` で安全。これらを切ると、他のサイトからの不正な操作を防ぐ仕組みが弱くなる。
- `server.enableStaticServing` が `true` にされていないか。初期値は `false`。

## 3. 不特定の人が使える状態

このアプリにはログイン機能がありません。自分の PC だけなら問題ありませんが、他の人が開けると話が変わります。

- 開いた人は全員、`.env` のキーで生成できる。**料金や利用枠は持ち主の負担になる。** 利用回数の制限もない。
- `st.cache_resource` や `st.cache_data` は利用者全員で共有される。キャッシュ（一時保存）に個人の情報を入れていないか。
- `st.session_state` は利用者ごとに分かれている。履歴はここにあるので、他の人からは見えない。

公開するなら、ログイン、利用回数の制限、Google 側の利用上限の設定が必要です。

## 4. ファイルアップロード

- `st.file_uploader` の `type` は拡張子で絞っているだけで、ファイルの中身は確かめない。
- `server.maxUploadSize` の初期値は 200MB。公開するなら小さくする。`upload.getvalue()` はメモリに全部読むので、大きなファイルはアプリを重くする。
- 読み込んだテキストをそのまま送ると、Gemini の利用料が増える。文字数の上限があるか。
- アップロードしたファイルをディスクに保存していないか。保存するなら、ファイル名をそのまま使うとフォルダの外に書き込まれるおそれがある。

## 5. AI の出力の表示

AI の出力は、信用できない入力として扱います。

- `unsafe_allow_html=True`、`st.html`、`components.html` に AI の出力や利用者の入力を渡していないか。渡すと XSS（他人の画面で勝手にプログラムを動かす攻撃）につながる。
- `st.markdown` は `<script>` などの HTML を動かさないので、その点は安全。ただし Markdown の画像 `![](https://...)` は表示されるので、**外部のサーバーに通信が発生する**。AI が悪意ある文書に誘導されて画像の URL に秘密の文章を埋め込むと、情報が外に送られる（下の6番と組み合わさる問題）。リンクも同様で、押すと外部サイトへ移動する。
- `st.code` に入れた文字列はそのまま文字として表示されるので安全。

## 6. プロンプトインジェクション

プロンプトインジェクションとは、文書の中に「これまでの指示を無視して〜」のような命令を紛れ込ませて、AI を操る攻撃です。

- 他人が作った PDF やテキストを要約するときに起こる。
- 被害の大きさは、**AI に何ができるかで決まる**。今のアプリの AI は文章を返すだけで、ファイル操作やネット接続の道具を持たない。起こりうるのは、出力の内容がおかしくなることと、5番の画像の問題くらい。
- AI に道具（関数呼び出し、URL の取得、ファイル操作など）を持たせる変更が入ったら、危険度を見直す。
- 会話の履歴が同じセッションに残っているので、前の文書の内容を画像の URL に埋め込ませることは理屈の上では起こりうる。

## 7. エラーと記録

- `st.error(f"...{e}")` のように例外の内容をそのまま画面に出していないか。公開すると内部の情報が見える。自分だけなら便利なので参考扱い。
- `print` や `logging` に入力の全文やキーを出していないか。
- `client.showErrorDetails` は、公開時には画面に出す情報を絞る設定を検討する。

## 8. 部品（ライブラリ）

- `pip-audit` の結果を確認する。
- `requirements.txt` が `>=` だけだと、入れ直すたびにバージョンが変わる。動いているバージョンの記録がないので、再現が難しい。公開するなら `pip freeze` で固定を検討する。
- 知らない名前の部品が増えていないか。

## 9. 追加された機能

既存のコードにない機能が増えたら、次を確認します。

- 利用者が入力した URL に接続する機能: SSRF（サーバーを踏み台にして内部のネットワークへ接続させる攻撃）に注意する。`http` と `https` だけを許可し、`localhost` や内部の IP アドレスを拒否し、タイムアウトとサイズの上限を設ける。リダイレクト先も確かめる。
- `eval`、`exec`、`pickle`、`subprocess`（特に `shell=True`）、`os.system`: 利用者の入力や AI の出力を渡すと、PC 上で任意のプログラムが動く。
- `open()` など、利用者が指定した名前でファイルを読み書きする処理: フォルダの外に出られないようにする。
- データベース: SQL は文字列をつなげて作らず、プレースホルダ（値を安全に差し込む仕組み）を使う。
- 外部サービスのキーやパスワードが増えていないか。`.env` で管理し、`.env.example` には項目名だけを書く。
