# セキュリティチェック

このアプリの安全性を調べて、プログラミングを学習中のユーザーが読んで判断できる報告書を作ります。

大切なのは、指摘の数を増やすことではありません。**このアプリで実際に何が起きるのか**を確かめて、優先順位をつけて伝えることです。一般論を並べると、本当に直すべき問題が埋もれてしまいます。

## 守ること

- **修正はユーザーが OK した項目だけ行う。** チェック中に変更してよいのは、報告書の新規作成だけです。git がないので、勝手に変更すると元に戻せません。
- **秘密の値を表示しない。** APIキーなどは、画面にも報告書にも書きません。報告書は人に見せることがあり、会話の記録も残るからです。`.env` を `cat` や Read で開かず、付属の `scan.py` の伏せ字の結果を使ってください。
- **本物の API を呼ばない。** チェックのためにアプリから Gemini API を呼ぶと、ユーザーの利用枠を使ってしまいます。
- **外部のサービスを攻撃しない。** 確認はコードを読むことと、自分の PC の中で動かすことに限ります。

## 手順

### 1. 使い方を確認する

同じコードでも、使い方によって危険度が変わります。依頼の内容から、次のどれかに決めてください。

| 使い方 | 例 |
| --- | --- |
| 自分の PC だけ | 特に説明がないとき（このアプリの基本の使い方） |
| 同じ Wi-Fi で共有 | 家族や同僚に使ってもらう |
| インターネットに公開 | Streamlit Community Cloud などに置く、友だちに URL を渡す |

依頼から分からなければ「自分の PC だけ」として進め、報告書にそう書きます。公開すると危険度が上がる項目は、その旨も書きます。

### 2. 機械でできる確認を行う

プロジェクトのフォルダで実行します。このスキルのフォルダの `scripts/scan.py` を使います。

```powershell
.\.venv\Scripts\python.exe <このスキルのフォルダ>\scripts\scan.py .
```

秘密の値らしき文字列、危険な書き方、設定の抜けを探して、伏せ字で一覧にします。ただしこれは手がかりです。出てきた項目は、手順4で本当に問題かを確かめてください。

### 3. 部品の弱点を調べる

pip-audit で、使っている部品に既知の弱点がないかを調べます。部品の名前とバージョンだけを外部のデータベースに問い合わせます。

```powershell
.\.venv\Scripts\python.exe -m pip_audit
```

入っていなければ、**ユーザーに確認してから** `.\.venv\Scripts\python.exe -m pip install pip-audit` で追加します。断られたときや実行できないときは、「部品の弱点は未確認」と報告書に書いてください。「問題なし」と書くと、調べていないのに安全だと誤解させてしまいます。

### 4. コードを読んで確かめる

`references/checklist.md` を読み、項目ごとに実際のコードを確認します。`app.py`、`gemini.py`、`tools.py`、`requirements.txt`、`.gitignore`、`.env.example`、`.streamlit/` を読んでください。チェックリストにない問題に気づいたら、それも報告します。新しく追加された機能は特に丁寧に見てください。

指摘にするのは、次の3つを説明できるものだけです。

1. **どこ**: ファイル名と行番号
2. **どうやって**: 誰が、何をすると起きるのか
3. **何が困るか**: お金、情報、PC への具体的な影響

説明できないものは指摘にせず、「確認できなかったこと」に書きます。すでに安全な部分は「問題なかったこと」に書きます。ユーザーが安心できますし、次の変更でその部分を壊さないようにも気をつけられます。

### 5. 危険度を決める

| 危険度 | 目安 |
| --- | --- |
| 🔴 高 | 今の使い方で、キーの流出、不正利用、PC への被害が現実に起こりうる。すぐ直す |
| 🟠 中 | 条件がそろうと起こる。または公開すると高になる。早めに直す |
| 🟡 低 | 被害が小さい、または起こりにくい。余裕があれば直す |
| ⚪ 参考 | 今は問題ないが、知っておくとよい |

手順1の使い方に合わせて判断します。たとえばログイン機能がないことは、自分の PC だけなら参考ですが、インターネットに公開するなら高です。

### 6. 報告書を作る

`security-reports/security-report-YYYYMMDD.md` に保存します（同じ日に複数回行うときは末尾に `-2` などを付けます）。次の形を使ってください。

```markdown
# セキュリティチェック報告書

- 実施日: YYYY-MM-DD
- 想定した使い方: 自分の PC だけ / 同じ Wi-Fi で共有 / インターネットに公開
- 調べた範囲: （調べたファイル、使った道具）

## まとめ

（結論を2〜3文で。今の使い方で安全か、最初に何をするべきか）

| 危険度 | 件数 |
| --- | --- |
| 🔴 高 | 0 |
| 🟠 中 | 0 |
| 🟡 低 | 0 |
| ⚪ 参考 | 0 |

## 見つかった問題

### 1. 🔴 （問題を一言で）

- **場所**: `app.py:123`
- **何が起きるか**: （誰が何をすると、どう困るのかを具体的に）
- **直し方**: （最小限の修正。コードや設定の例も）
- **手間**: 小 / 中 / 大

## 問題なかったこと

## 確認できなかったこと

## 公開するなら追加で必要なこと

（「インターネットに公開」以外のときに、公開前に必要なことを短く）
```

専門用語はできるだけ避け、使うときは短く意味を添えてください。例: 「XSS（他人の画面で勝手にプログラムを動かす攻撃）」。

### 7. 結果を伝えて、修正の希望を聞く

会話では、まとめと優先して直す項目だけを短く伝え、報告書の場所を示します。そのあと「どの番号を直しますか？」と聞いて、いったん止まってください。

### 8. OK が出た項目だけ直す

1. 変更するファイルを `backup/YYYYMMDD/` にコピーします。
2. OK が出た項目だけを、できるだけ小さな変更で直します。
3. 直った部分を確認します。`app.py` などを変更したら、構文を確認してアプリが起動するかを見てください。ただし、手順の「守ること」のとおり本物の API は呼びません。
4. 何を変えたかと、ユーザー自身の作業（キーの作り直しなど）が残っていないかを伝え、報告書に修正結果を追記します。
